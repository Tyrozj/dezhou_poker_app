# CoCo 云房间 / 云数据表 接入方案

本文说明本项目与 [CoCo](https://coco.codemao.cn/)（编程猫 CoCo 编辑器）的「云房间」「云数据表」两个云工具如何配合，哪种方式能真正上线、哪种方式只是教学演示。

---

## 0. 三句话结论

1. **CoCo 云房间是"作品内部"的广播通道，云数据表是"作者账号下"的表格，两者都没有对外的 HTTP/WebSocket 接口**，外部网页或自建服务器无法直接读写它们，只能由 CoCo 作品里的积木/自定义控件访问。
2. 德州扑克必须有**私有信息**（底牌只给本人）和**权威裁决**（不能由玩家自己算），而云房间的消息是**广播给房间内所有人**的 → 底牌与裁决不能放在云房间里做，必须有一个服务端。
3. 所以推荐：**H5 前端 + 本项目服务端**（可直接玩），CoCo 侧用「网页框」嵌入并打包成 APP；或者用「HTTP客户端」积木把 CoCo 作品接到本服务端的 REST 接口上。云数据表则按本文件的字段表保存「房间表 / 战绩表」。

---

## 1. CoCo 这两个工具能做什么

### 云房间（官方积木）

| 积木 | 作用 |
| --- | --- |
| 创建房间（"房间名"）房间人数 (N) | 用房间名创建房间，人数上限固定 |
| 设置我在房间的昵称（"昵称"） | 进入前的必经步骤 |
| 进入房间（"房间名"） | 房间名即唯一标识 |
| 发送房间消息（列表） | 把一条消息广播给房间内所有人 |
| 当收到房间消息（列表） | 收到别人广播的消息 |
| 当收到房间通知［进入房间］（用户名） | 有人进出房间时触发 |
| 当前进入的房间名 / 当前进入的房间人员列表 | 读取房间状态 |
| 获取房间列表 / 退出房间 | 列表与退出 |

关键特征：**全房间广播、无私有消息、无服务端计算、房间名唯一**。

### 云数据表（官方积木）

新增行、删除行、更新行、查询（某列 = 某值的行）、查询行数/列数、清空；**单元格的值都是字符串**；数据源跟随作者账号，一个数据源可被多个作品引用；测试环境与正式环境共用同一数据源。

---

## 2. 为什么牌局裁决必须在服务端

- **底牌隐私**：云房间只能广播。若把发牌结果广播出去，任何玩家抓包都能看到别人的底牌，游戏直接失去意义。
- **防作弊**：下注合法性（最小加注、短码全下、边池）必须由可信的一方差；如果由某位玩家手机计算，他可以篡改。
- **断线一致性**：重连后需要拿到"当前这一手的权威状态"，纯 P2P 很难保证。

本项目的做法：洗牌与牌局状态只存在服务端，每个连接只收到为自己定制的视图（别人的 `cards` 为 `null`），摊牌时才公开。

## 3. 方案 A：CoCo「网页框」+ 本服务（推荐）

适合：想马上能用、要真联机、想打包成安卓 App。

步骤：

1. 把本项目跑在一台**有公网地址**的机器上（云服务器 / 内网穿透 / 公司内网都行），拿到形如 `https://poker.example.com/` 的地址。
   - CoCo 网页框在打包后的 App 里加载远程页面，**建议用 https**；本项目会自动把 WebSocket 切成 `wss://`。
2. CoCo 编辑器新建作品 → 添加「网页框」控件 → 填上面这个地址 → 铺满屏幕。
3. 作品里另加两个按钮（可选）：「房号说明」「刷新」，用积木调用网页框的刷新即可。
4. 作品 → 打包 APP，得到安卓安装包；用户装上后用同一个页面联机。
5. 云数据表（可选）：把 `data/rooms.json` → 「房间表」、`data/hands.jsonl` → 「战绩表」的字段照着第 5 节建好，做一个"战绩查询"页面（或者在服务端把这两张表同步进云数据表，见第 6 节）。

优点：功能完整、真联机、可打包；缺点：需要一个可访问的服务端。

---

## 4. 方案 B：CoCo 作品 + 本服务 REST 接口

适合：想在 CoCo 里自己画界面（列表、按钮、对话框），把本项目当作"云函数 + 云数据库"。

### 4.1 接口与积木的对应关系

CoCo 的「HTTP客户端」积木支持 GET/POST，并返回文本；把返回的 JSON 用「字典/列表」积木解析即可。

| 需要做的操作 | 调用 | 参数 | 返回 |
| --- | --- | --- | --- |
| 刷新房间列表 | `GET /api/rooms` | — | `{rooms:[{code,name,players,seats,sb,bb,phase}]}` |
| 创建房间 | `POST /api/rooms` | `{nickname, name, settings:{seats,startChips,sb,bb,actionSeconds,autoStart}}` | `{code,token,playerId,seat}` |
| 加入房间 | `POST /api/rooms/:code/join` | `{nickname, token?}` | `{token,playerId,seat}` |
| 轮询牌桌状态 | `GET /api/rooms/:code/state?token=..&since=..&wait=20` | 长轮询，最多等 20 秒 | `{seq, state:{table:{...}}}` |
| 行动 | `POST /api/rooms/:code/action` | `{token, action:{type:"fold|check|call|raise|allin", to?}}` | `{ok, state}` |
| 开局 / 补码 / 旁观 / 移出 / 退出 | `POST /api/rooms/:code/start｜rebuy｜sitout｜kick｜leave` | `{token,...}` | `{ok}` |
| 旁观（不含底牌） | `GET /api/rooms/:code/view` | — | `{room, table}` |

> `token` 是这个玩家的凭证（相当于登录态），创建/加入后保存到变量里，之后所有请求都带上；重连时带上同一个 token 就能回到原座位。

### 4.2 积木流程（伪代码）

```
当 绿旗被点击:
  设置 [昵称] 为 (输入框内容)
  用 HTTP客户端 POST (服务器地址 & "/api/rooms") 体 {"nickname": 昵称, "settings": {...}}
  把 返回的 code  放进 [房号]
  把 返回的 token 放进 [我的token]
  进入轮询

当 我想加入:
  用 HTTP客户端 POST (服务器地址 & "/api/rooms/" & [房号] & "/join") 体 {"nickname": 昵称}
  ...

轮询（用"重复执行 + 等待 0.2 秒"或递归自定义积木）:
  用 HTTP客户端 GET (服务器地址 & "/api/rooms/" & [房号] & "/state?token=" & [我的token] & "&since=" & [上次seq])
  如果 返回里有 state:
    设置 [上次seq] 为 返回的 seq
    把 state.table.seats 渲染成 座位列表
    把 state.table.pot / board / actorSeat 更新到界面
    如果 state.table.you.legal 不为空（轮到自己）:
      显示 弃牌 / 过牌 / 跟注 / 加注 / 全下 按钮
```

要点：
- `state.table.you` 是**你自己的座位视图**（含 `legal` 合法动作和 `cards` 自己的底牌）；`state.table.seats[i]` 是公开座位信息。
- 轮询用长轮询（`wait=20`）：没有变化时请求会挂起 20 秒再返回，比每秒轮询省流量，也更快。
- 有变化立刻返回；返回里的 `seq` 用作下次的 `since`。

### 4.3 云房间在方案 B 里的角色

云房间不做牌局通信，只做"轻通知"，例如：

- 创建房间时同时用积木「创建房间（"dz-" + 房号）人数 (N)」并在作品里「进入房间」，这样房间成员列表 = 在线玩家；
- 有人进房时用「发送房间消息」广播 `{"t":"hi"}`，其他人「当收到房间消息」时把提示条闪一下（"有人催你出牌"）；
- 摊位/牌桌上方的"在线人数"直接用「当前进入的房间人员列表」的数量。

**不要**把底牌、下注金额等裁决数据放进云房间——那是广播。

### 4.4 云数据表在方案 B 里的角色

见第 5 节字段表：创建/更新房间行、每手结束新增战绩行。查询用「查询云数据表 中（第1列）（=）（房号）的数据」，返回值是二维列表，需要用两次「列表取项」取值。

## 5. 云数据表建表字段

### 表一：房间表（对应 `data/rooms.json`）

| 列 | 字段 | 示例 | 说明 |
| --- | --- | --- | --- |
| 1 | 房间号 | `522605` | 主键，创建时写入 |
| 2 | 房间名 | `周末局` | |
| 3 | 人数上限 | `4` | 2–8 |
| 4 | 起始筹码 | `1000` | |
| 5 | 小盲 | `10` | |
| 6 | 大盲 | `20` | |
| 7 | 状态 | `waiting/betting/showdown` | 每次状态变化更新 |
| 8 | 局数 | `7` | 已进行的手数 |
| 9 | 房主 | `阿宝` | |
| 10 | 更新时间 | `1730000000000` | 毫秒时间戳 |

写入时机：创建房间时**新增行**；牌局状态/局数变化时**更新行**；房间回收时**删除行**。

### 表二：战绩表（对应 `data/hands.jsonl`）

| 列 | 字段 | 示例 |
| --- | --- | --- |
| 1 | 房间号 | `522605` |
| 2 | 局号 | `7` |
| 3 | 时间 | `1730000000000` |
| 4 | 公共牌 | `2h 7d Qs Js 2c` |
| 5 | 底池 | `320` |
| 6 | 赢家 | `老王` |
| 7 | 赢家金额 | `320` |
| 8 | 牌型 | `三条 2` |

写入时机：每手结束（摊牌或其他人弃牌）时**新增一行**。

> 注意：云数据表的单元格都是字符串，数字要自己转；一个数据源被多个作品共用，调试数据会污染正式数据——建议正式发布前清空一次。

## 6. 把本地文件存储换成云数据表

服务端的存储层是一个很小的接口（`server/store.mjs`）：

```js
upsertRoom(row)     // 房间表：新增/更新一行
removeRoom(code)    // 房间表：删除一行
roomRows()          // 房间表：查询全部
insertHand(record)  // 战绩表：新增一行
recentHands(n)      // 战绩表：最近 N 行
```

需要说清楚的一点：**云数据表只有 CoCo 作品自己能写**，没有给外部服务端调用的公开接口。所以"把存储换成云数据表"只有两种务实做法：

**做法 1（推荐）：服务端权威 + 作品侧同步**
服务端继续用 `data/*.json` 保存权威数据，并在两个时机把同样的数据"给到"作品，由作品写进云数据表：

- 作品定时 `GET /api/rooms/rows` 和 `GET /api/hands?n=30`，拿到与服务端**字段完全一致**的行，用「删除行 + 新增行」覆盖对应房号的数据；
- 或者作品每局结束时 `GET /api/hands?n=1`，只追加最新一手。

这样云数据表里的房号、人数、盲注、赢家、底池等字段与第 5 节完全对应，社区里可以做一个"战绩查询"作品读这张表。

**做法 2：让云数据表成为唯一存储（可选）**
如果你只想要"社区战绩榜"，可以让作品在每手结束时把战报写入云数据表，服务端的 `data/hands.jsonl` 仅作为本地副本便于排查。房间本身仍然是内存态——云数据表没有原子锁，不适合承载实时牌局状态。

> 想要"服务端直接写云数据表"是不可行的（没有公开接口）；如果你确实需要，只能自己在服务端实现一个能访问 CoCo 账号的代理，这超出本项目的范围，也有合规风险，不建议。

## 7. 方案 C：纯 CoCo 积木 / 自定义控件（不推荐）

如果一定要"零服务器"，只有两条路：

1. **把裁判写在积木里**：洗牌、发牌、下注校验、边池、牌型比较全部用积木实现——相当于把 `server/table.mjs`（约 700 行逻辑）翻译成积木，工作量大且几乎无法维护。
2. **房主当荷官**：房主手机负责洗牌与裁决，通过云房间广播"某某的行动"，底牌私下告知（云房间做不到私聊，只能用"房主把底牌编码后广播、只有对应玩家能解"的障眼法，实际上所有人都能解）。
   - 可以用"承诺-公开随机种子"减少房主作弊空间（开局前所有人提交随机数哈希，结束后公开种子复核牌堆），但房主仍能看到所有底牌。

结论：方案 C 适合课堂演示"多人联机"概念，不适合真实对战。

## 8. 踩坑清单

- **云数据表单元格都是字符串**：`"1000"` 不是 `1000`，比较大小要先转数字。
- **数据源跟账号走**：协作作品里，协作者不能用「选择数据源」，必须由作者绑定。
- **测试数据会污染正式数据**：云数据表不区分测试/正式环境。
- **网页框**：打包后的 App 需要能访问你的服务地址；https 页面里连 `ws://` 会被浏览器拦，本项目会自动改用 `wss://`，所以服务端要配好 TLS。
- **云房间人数上限是创建时固定的**，且房间名唯一，建议用 `dz-房号` 这种前缀避免撞名。
- **云房间消息是广播**，不要在里面传底牌、token 等敏感数据。
